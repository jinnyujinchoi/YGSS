## 0. 전체 개요

### 배경
YGSS의 RAG 챗봇 시스템에는 임계값 0.45가 근거 없이 하드코딩되어 있다는 문제 외에도, 코드 리뷰 결과 더 결정적인 결함이 발견되었다.

1. **한국어 Q&A를 영어 Cross-Encoder(`ms-marco-MiniLM-L-12-v2`)로 평가** — 의미 평가 자체가 무작위에 가까움
2. **2단계 retrieval 파이프라인의 4개 매직 넘버**가 각기 다른 파일에 분산
3. **평가 도구 부재** — 무엇을 바꿔도 좋아졌는지 증명할 방법이 없음

### 리팩토링 목표
- 운영 RAG 시스템의 retrieval 품질을 정량 측정 가능하게 만든다
- 영어 모델로 한국어를 평가하던 결함을 한국어 모델로 교체한다
- 4개 파라미터(Bi-Encoder 임계값, top-K, Cross-Encoder 임계값, top-3)의 최적 조합을 grid search로 도출한다

### 산출물의 활용
- 백엔드 Java 코드는 본 리팩토링에서 직접 수정하지 않는다.
  - STEP A에서는 백엔드 Java와 운영 AI 서버 코드를 모두 수정하지 않는다.
  - STEP B에서는 AI 서버의 Cross-Encoder 교체를 위해 ai/src/api/routes/server.py만 수정한다.
  - STEP C에서는 백엔드 Java의 임계값/top-K 변경은 직접 수정하지 않고, 권장 변경 라인과 patch 제안으로만 제출한다.
- 모든 평가/실험 코드는 ai/experiments/rag_eval/ 하위에 독립적으로 작성한다.
- 운영 적용 대상과 실험 대상은 명확히 분리한다.

## 1. 작업 순서 결정 근거

총 3단계로 분할하며, 의존성 분석 결과 **A → B → C** 순서로 진행한다.

| 단계 | 작업 | 산출물 | 의존성 |
|---|---|---|---|
| **STEP A** | RAG 평가 프레임워크 구축 | 평가 셋 + Precision/Recall 측정 파이프라인 | 외부 의존만 (OpenAI API) |
| **STEP B** | Cross-Encoder 한국어 모델 교체 | `server.py`의 모델 + 점수 임계값 변경 | STEP A의 평가 도구 필수 |
| **STEP C** | 4-parameter grid search | 최적 파라미터 조합 + 운영 적용 PR | STEP A, B 모두 필수 |

**왜 이 순서인가:**
- 평가 도구 없이 모델을 먼저 교체하면 "왜 바꿨고 얼마나 좋아졌는지" 증명 불가
- 새 한국어 모델의 점수 임계값도 측정 없이 정하면 또 다른 매직 넘버가 됨
- 평가 도구 → 모델 비교/선정 → 전체 grid search 순서가 인과 사슬이 자연스러움

## 2. 브랜치 전략

본 작업은 master에 직접 반영하지 않는다.
master 하위에 refactor 브랜치를 생성하고, RAG 리팩토링 관련 작업은 모두 refactor 브랜치를 기준으로 분기한다.

브랜치 구조는 다음과 같다.

```
master (보호 브랜치)
└── refactor
      ├── refactor/rag-eval-framework        ← STEP A
      │       │ (작업 완료 후 PR → master)
      │       ▼
      ├── refactor/ko-cross-encoder          ← STEP B (A 머지 후 분기)
      │       │ (작업 완료 후 PR → master)
      │       ▼
      └── refactor/rag-grid-search           ← STEP C (B 머지 후 분기)
            │ (작업 완료 후 PR → master)
            ▼
            master
```

작업 순서는 다음과 같다.

1. master에서 refactor 브랜치를 생성한다.(생성 완료)
2. refactor에서 refactor/rag-eval-framework 브랜치를 생성한다.
3. 평가 프레임워크 작업 완료 후 refactor로 머지한다.
4. 최신 refactor에서 refactor/ko-cross-encoder 브랜치를 생성한다.
5. Cross-Encoder 교체 및 평가 작업 완료 후 refactor로 머지한다.
6. 최신 refactor에서 refactor/rag-grid-search 브랜치를 생성한다.
7. 파라미터 튜닝 및 매직 넘버 제거 작업 완료 후 refactor로 머지한다.
8. refactor에서 전체 실험 결과와 코드 동작을 검증한 뒤 master로 최종 PR을 생성한다.

### 규칙
- 각 작업 브랜치는 반드시 최신 refactor에서 분기한다.
- 작업 브랜치끼리 직접 머지하지 않는다.
- master에는 개별 작업 브랜치를 직접 머지하지 않는다.
- master로는 refactor 브랜치만 최종 머지한다.
- 각 브랜치는 **이전 단계가 refactor에 머지된 뒤** 분기한다 (병렬 작업 금지)
- 각 PR은 **단일 STEP의 산출물만 포함**한다 (스코프 혼합 금지)
- 커밋 컨벤션: `refactor:`, `feat:`, `test:`, `docs:`, `chore:` 접두어 사용
- PR 본문에는 "Before/After 측정값"을 반드시 포함한다 (STEP A 산출 도구 활용)

## 4. STEP B — Cross-Encoder 한국어 모델 교체

### 브랜치
`ko-cross-encoder` (from `refactor`, **STEP A 머지 후 분기**)

### Codex 프롬프트

```

프로젝트: YGSS
레포 루트: /Users/jinnysmacbookair/DEV/YGSS

전제: STEP A의 ai/experiments/rag_eval/ 평가 프레임워크가 master에 머지된 상태

현재 결함:
- ai/src/api/routes/server.py 의 CrossEncoder 모델이 영어 전용

- 한국어 Q&A를 영어 모델로 평가 → 의미 평가 무작위 수준
- 점수 임계값 6 (filtered = [(c, s) for c, s in ranked if s >= 6])이 근거 없음

건드리면 안 되는 부분:
- backend/ 디렉토리 전체
- ai/src/api/routes/ 의 server.py 외 다른 파일
- ai/experiments/rag_eval/ 의 기존 public interface
  - 단, cross_encoder.py 확장과 experiments/cross_encoder_comparison.py 추가는 허용한다.
```

## 8. 향후 후속 작업 (이번 리팩토링 범위 외)

현재 코드 리뷰에서 발견되었으나 이번 작업 범위에 넣지 않은 항목들. 별도 리팩토링 사이클에서 다룬다.

- **Jedis → JedisPool 전환** (thread-safety 이슈)
- **Redis Vector Search (HNSW) 도입** (현재 O(N) 풀스캔 → 확장성 한계)
- **ChatBotServiceImpl의 거대 try-catch 분해** (관측 가능성)
- **하드코딩된 fallback 포트폴리오 제거** (장애 은폐)
- **GPT/Gemini 양쪽 빌드되는 죽은 코드 정리**
